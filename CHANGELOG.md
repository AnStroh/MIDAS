# Changelog

All notable changes to MIDAS are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [CITATION.cff](CITATION.cff).

## [Unreleased]

### Added

- `octave/MIDAS_GUI.m` - an interactive front-end for `octave/`, covering the same fields, six examples, Run/Reset, Save/Load Preset, Export Data/Figures, and Manage Results as `GUI/MIDAS.m`. Built from scratch with plain `figure`/`uicontrol` rather than ported, since Octave has no App Designer, `uigridlayout`, or `uitabgroup` to build against, and can't open `.mlapp` files at all. Does not yet include the MATLAB GUI's dark/light toggle. See [`docs/gui.md`](docs/gui.md#octave-gui).
- `tests/` - a cross-implementation consistency check: runs the same six examples through `matlab/`, `GUI/`, and `octave/` and diffs the full result struct field by field (default tolerance `1e-12`), rather than just checking that each runs without crashing. See [`tests/README.md`](tests/README.md).
- `addSoftwareStamp.m` (all three folders) - extracted out of `export_pub_fig.m` (previously a private local function there) into its own file, so `MIDAS_Main.m`'s movie-writing code can call it too: every GIF frame and `_movie_t*.jpg` now carries the same "MIDAS - Stroh & Moulas (2026)" attribution as PDF/PNG exports already did. Closes the gap where a GIF or movie JPG pulled out of context had no way to trace back to the software that made it (`.mat`/`.xlsx` exports already carried `R.software` - see Corrected below).
- `validateCoreParams` (new local function in `MIDAS_Main.m`, all three folders, called at the very top) - fails fast with one precise, plain-language message per problem field (naming the field, its actual value, and why it matters) for `CFL`, `t_tot`, `lxA`, `lxB_factor`, `nx_A`, `nx_B`, `DRG`/`DRG_LuHf`/`DRG_Mn`/`DamA`/`DamB`. Checks are NaN-safe (`~(x > 0)` rather than `x <= 0`), since a NaN - e.g. from a GUI numeric field that got non-numeric text - silently passes any `<=`/`<`/`>=` comparison.
- A guard in the `eqMode = 'poly'` branch of `MIDAS_Main.m` (all three folders): errors clearly, naming the exact problem and two concrete fixes, if `Tar`/`Par`/`Car_G`/`Car_B` still contain their `MIDAS_Params.m` `[NaN,NaN,NaN]` placeholders - instead of silently fitting a polynomial to NaN and producing a finite-looking but scientifically meaningless result (see Fixed below).

### Removed

- `'interpreter','latex'` (and `$`-delimited LaTeX math mode) across every plotting file in `octave/` - Octave's LaTeX renderer fails its own startup self-test on this install and disables itself (see Known limitations below), so every `'latex'`-interpreted label was showing raw markup verbatim (`$^{176}$Hf`, `$\Delta T$`, literal dollar signs) instead of being typeset - confirmed visually by rendering a real figure to PNG and inspecting it. Removed the interpreter argument entirely (now defaults to Octave's `'tex'` interpreter) and stripped `$` delimiters from every label string; backslash commands the codebase actually uses (`\Delta`, `\tau`, `\max`, `^{...}`, `_{...}`, `^o`) all render correctly under plain `'tex'` with no changes needed - confirmed by direct visual comparison (Greek letters, super/subscripts, and the degree symbol all render correctly; `\%` does not - `'tex'` doesn't recognize that LaTeX-specific escape, so it was separately unescaped to a plain `%` everywhere it appeared). As a side effect, this also fixed the y-axis tick labels themselves appearing mirrored/corrupted, which turned out to be a knock-on effect of the same broken LaTeX renderer state rather than a separate bug. Scoped to `octave/` only - MATLAB's LaTeX rendering isn't affected by this Octave-specific issue, so `matlab/`/`GUI/` keep `'latex'` throughout, unchanged.

### Fixed

- **Adversarial/beginner-mistake testing pass** (both a programmer trying edge cases, and a non-programmer domain scientist fat-fingering values) surfaced several real correctness/usability bugs, now fixed and verified in `octave/` (mirrored, but not execution-verified, in `matlab/`/`GUI/`):
  - `params.CFL <= 0` (most notably `CFL = 0`, an easy typo) made the adaptive time step `dt = 0` - the run never advanced and hung forever with no error and no output. Now caught by `validateCoreParams` (see Added) before the run starts.
  - A missing/misnamed `params.PD` phase-diagram file correctly triggers `MIDAS_Main`'s existing `eqMode: 'PD' → 'poly'` fallback, but that fallback then used the default `MIDAS_Params()`'s `Tar`/`Par`/`Car_G`/`Car_B` - which are `[NaN,NaN,NaN]` placeholders, only ever meant to be set when `eqMode = 'poly'` is chosen deliberately (see e.g. `MIDAS_Params_Example2_PolyEquilibrium.m`). Fitting a polynomial to NaN produced a singular-matrix warning on the first call, which then propagated into `isochronsRef` calling `polyfit` on degenerate data on nearly every timestep - **17,553 lines of warnings for a 1 Myr test run** - while `R.S_final` stayed finite and plausible-looking even though `R.CA_final`/`CB_final`/`tALuHf1_final` correctly came out `NaN`. Since `.github/scripts/smoke_test.m`'s only pass criterion was `isfinite(R.S_final)`, this exact failure mode would not have been caught by CI. Now caught explicitly (see Added); `smoke_test.m` was also hardened to check `CA_final`/`CB_final`/`tALuHf1_final` for NaN, not just `S_final`.
  - `octave/MIDAS_GUI.m`'s numeric fields are plain text `uicontrol`s (Octave has no native numeric-only edit field like MATLAB's `uieditfield(...,'numeric')`), so non-numeric text typed into one produced `NaN` via `str2double`, which then silently passed every one of `validateParams`'s `<=`/`<` guard checks (`NaN <= 0` is `false`) straight through to `MIDAS_Main`. Both GUIs' `validateParams` now use the same NaN-safe comparison pattern as `validateCoreParams`.
- `octave/` port: verified for the first time by actually running it under a real Octave interpreter (11.3.0) rather than logic-checking against MATLAB only, surfacing and fixing several real bugs:
  - `griddedInterpolant` (used for the P-T path lookup in `MIDAS_Main.m`) does not exist in Octave at all - replaced with `interp1(...,'extrap')` anonymous functions.
  - `tiledlayout`/`nexttile` do not exist in Octave either, contrary to this port's own `octave/README.md` claim that Octave 7.1+/8.x has them - added `octave/tiledlayout.m` and `octave/nexttile.m` as drop-in shims (backed by `subplot`), so the 7 affected plotting scripts needed no changes.
  - MATLAB-style dot-notation property access on graphics handles (`cb.Label.Interpreter = ...`, `lgd.FontSize = ...`, `titles.handles(i).String = ...`) throws `scalar cannot be indexed with .` in Octave - converted to `get`/`set` calls across `plot_them_1.m`, `plot_them_3.m`, `plot_velocity_age.m`, `MIDAS_Main.m`, `export_pub_fig.m`.
  - `round(x,n)` (MATLAB's two-argument, round-to-n-decimals form) isn't supported by this Octave's `round` - replaced with `round(x*10^n)/10^n` in `plot_them_2.m`/`plot_them_3.m`.
  - The new `tiledlayout.m` shim didn't clear previously-drawn axes on repeated calls the way MATLAB's real `tiledlayout` wholesale-replaces its layout every call - `subplot`-reused axes silently carried over prior lines/legend entries/annotations, accumulating them frame-over-frame during a live-updating run (visible as a growing legend and cluttered/overlapping panels). Now deletes existing axes first.
  - The new `nexttile.m` shim always returned its axes handle regardless of `nargout`, unlike MATLAB's real `nexttile` (which only assigns a return value when the caller asks for one) - caused `ans = ...` to spam the console on every bare `nexttile(n)` call. Fixed to check `nargout`.

### Corrected

- An earlier finding in this entry claimed `.xlsx` exports carry no MIDAS attribution anywhere in their content. That was based on grepping `export_results_excel.m`'s own source for the literal word "MIDAS," which can't see a runtime value - `R.software` (a plain char field, `'MIDAS - Stroh, A. & Moulas, E. (2026)'`) is in fact written into the Summary sheet/CSV by the function's existing generic scalar/text field export loop, confirmed by actually generating one and checking its content. Only the GIF/movie-JPG gap (see Added/Fixed above) was real.

### Changed

- `export_pub_fig.m` (`matlab/`, `GUI/`, `octave/`): PDFs now also export at 300 dpi for any rasterized content within them (contourf/pcolor fills, etc.), via `exportgraphics(...,'Resolution',300)` / `print(...,'-r300')` - previously only the companion PNG specified a resolution.
- Model description (`README.md`, `docs/index.md`, `CITATION.cff`, and the `MIDAS_Main.m` header in all three folders): generalized from "a garnet crystal growing in a matrix" to a general phase-A-mineral/phase-B-matrix-phase framing, with the garnet-biotite pair now named explicitly as the example used throughout this repository; also spells out the MIDAS acronym (Mineral Interface Dynamics and apparent-Age Simulation) inline.
- `README.md`/`docs/index.md`: added a development-status note - v0.1.0, interfaces/defaults/file formats may still change, known limitations tracked here.

### Known limitations

- This Windows Octave install - checked for both the `winget install GNU.Octave` package and the official `octave.org` 11.3.0 Windows installer, which produced an identical result - ships only the `fltk` and `gnuplot` graphics toolkits; `qt` (the toolkit Octave's own runtime warnings recommend, and normally the default on other platforms) is unavailable (`available_graphics_toolkits()` never lists it, and no Qt DLLs exist anywhere under the install tree). `print()`/`exportgraphics` always route through `fltk` for rasterization regardless of which toolkit is set active.
  - LaTeX label rendering failing its own startup self-test is now worked around (see Removed above) rather than left broken - `octave/` no longer requests the `'latex'` interpreter anywhere.
  - Exporting any figure with 2-D color-mapped content (`print()`/`exportgraphics` to PNG/PDF) still hangs indefinitely (`GL2PS warning: Unknown token in buffer`, then no further progress) - confirmed this is **not** specific to `contourf`: `pcolor` and `imagesc` were both tested as potential substitutes and hang identically. This is a broader `fltk`/GL2PS limitation affecting any rasterized/shaded 2-D content, not something a different plotting function choice can route around; still unresolved, still needs a working `qt` toolkit. Avoid `saveCheckpoints`/figure export for the phase-diagram panels (or any color-mapped plot) under Octave on Windows until then.
- `docs/octave.md` states `ci-octave.yml` "exercises [the port] under a real Octave interpreter on every push," but `.github/scripts/smoke_test.m` sets `doPlot = false` throughout, so it never actually exercises `MIDAS_Main.m`'s own live-plotting branch (where the `griddedInterpolant` bug above lived). It does call `plot_velocity_age.m` and other standalone plotting functions directly, which use `tiledlayout` and should fail on any genuine Octave install (which has never had `tiledlayout` built in) - whether that CI job has actually been passing or failing was not confirmed here (private repository, not checked).
- `octave/MIDAS_GUI.m` has no dark/light toggle yet (the MATLAB GUI's is not yet ported). Also, in a non-interactive batch test, closing its window (many nested panels/controls) crashed the Octave process during cleanup on the `fltk` toolkit - consistent with the other `fltk` limitations above rather than a bug in the GUI's own logic, but not yet confirmed either way against closing the window normally in an interactive session. Report back if this reproduces interactively.
- `.github/scripts/smoke_test.m`'s full pipeline had never actually been run to completion under Octave before now - running it end-to-end surfaced (and fixed) four more real Octave-compatibility bugs beyond the ones already listed above:
  - `legend('Location','best', ...)` was originally suspected as the trigger for a hard crash deep inside Octave's own `legend.m` (`kids(1): out of bound 0 (dimensions are 0x0)`, from `legend>create_item`) in `plot_massbalance.m`. Changing the location to `'northeast'` alone did **not** fix it - isolated repros narrowed the real cause down to `yline(0,'Color',[0.7 0.7 0.7],'HandleVisibility','off')` on the same axes: a plain `yline(0,'--')` (no `HandleVisibility`) followed by `legend(...)` is fine, but adding `'HandleVisibility','off'` to it crashes `legend()` outright, regardless of the requested location. Fixed in `plot_massbalance.m` by replacing that `yline` with an equivalent `plot(xlim,[0 0],...,'HandleVisibility','off')` (avoids `yline` entirely); `plot_misfit.m`/`plot_massbalance.m`'s legend locations were changed to `'northeast'` while investigating and left there (harmless, already verified working) rather than reverted back to `'best'`.
  - `params.make_movie = 1` had never actually worked under Octave at all, independent of the toolkit issues above: `[imind,cm] = rgb2ind(im,256)` (MATLAB's image-plus-colorcount calling form) isn't a valid Octave signature (`Invalid call to rgb2ind`). Fixed by dropping the second argument (`rgb2ind(im)`) - 256 was already GIF's own hard maximum and MATLAB's own default when omitted, so this changes nothing about the output on either platform. Applied in `octave/MIDAS_Main.m` only (the bug is Octave-specific; not yet confirmed whether the two-argument form is valid under real MATLAB, so `matlab/`/`GUI/` were left as-is).
  - `parula(n)` (used to colormap several fixed-position/time-series line plots) doesn't exist in Octave at all - replaced with `viridis(n)`, Octave's own closest perceptually-uniform equivalent (a plain callable function there, unlike in MATLAB), in `plot_age_at_fixed_positions.m`, `plot_conc_at_fixed_positions.m`, `plot_age_vs_temperature.m` (`octave/` only - `parula` exists natively in MATLAB, so `matlab/`/`GUI/` are unaffected and unchanged).
  - `sgtitle(...)` (the whole-figure title in `plot_initial_conditions.m`) doesn't exist in Octave either - added an `exist('sgtitle',...)` check that falls back to an `annotation('textbox',...)` spanning the top of the figure when it's unavailable, matching a pattern `export_pub_fig.m` already used defensively for the same reason. Note: unlike a real `sgtitle`, this fallback annotation isn't picked up by `export_pub_fig.m`'s title-hiding logic, so it still shows in the `_notitle` exported variant - a minor cosmetic gap, not fixed here.

## [0.1.0] - 2026-08-28

Initial version.

### Added

- Three independent, self-contained copies of the model: `matlab/` (command-line/scripts), `GUI/` (interactive MATLAB App Designer front-end, `MIDAS.m`), and `octave/` (GNU Octave port) - identical physics and identical default parameters across all three.
- Six standalone example configurations (`MIDAS_Params_Example1_Baseline` through `Example6_CylindricalGeometry`), each a complete, self-contained parameter set with every field it doesn't use set to `NaN`, exercising every mode switch in the model. All six run to completion at full grid resolution with physically sensible (net-growth) results.
- GUI: **Load Example** dropdown + button - pick any of the six examples (or plain `MIDAS_Params`) and populate every field from it as a starting point; every field stays freely editable afterwards. Plus a **dark/light toggle** (header, next to the logo) that re-colors backgrounds, panel titles, and field labels and swaps the logo image.
- Boundary conditions (`implicitDiffusionSolver.m`): the center of the domain (x=0) is always Neumann for cylindrical/spherical geometry (`ndim` = 2, 3), as required by symmetry, regardless of `NBC`; the outer edge of phase B always follows `NBC` freely (Neumann or Dirichlet), for every geometry.
- `plot_initial_conditions.m` - every element/isotope's initial ($t=0$) profile, phase A vs. phase B, one figure (the "before" to `plot_all_composition_profiles`'s "after").
- Figures export as a vector PDF + PNG, both a titled and an untitled version, with a small attribution stamp (`export_pub_fig.m`). Nothing is written to disk by default otherwise - `save_data`, `make_movie`, and every per-figure `save_*` flag in `Run_MIDAS.m` start off; opt in per field.
- CI: `ci-matlab.yml`, `ci-gui.yml`, `ci-octave.yml` (smoke-test all six examples plus the full plotting/export pipeline on every push - `.github/scripts/smoke_test.m`), `docs.yml` (GitHub Pages), and `spellcheck.yml`.
- Full documentation site (`docs/`): getting started, examples, configuration options, equations/theory, mesh & time-step refinement, interpreting output, benchmarks, phase-diagram (Perplex) setup, references, API reference, GUI guide, and Octave notes - with the MIDAS logo (light/dark-aware) on every page.
- `LICENSE` (MIT), `CITATION.cff`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`.

### Known limitations

- No formal unit test suite yet - CI runs the six examples as a smoke check only (see [Testing](README.md#testing)).
- Mass-balance drift (a numerical-integrity check with no expected physical source/sink) is small for MgO but unexpectedly large for MnO/Hfr in full-length runs. Investigated in depth; not yet fixed, paused for now. Confirmed: the partition-coefficient *jump size* at the interface is a  real driver (forcing `KDMn` to `5`, MgO's own ratio range, cuts `dMBMn_max` 10x; `DRG_Mn` alone has no effect). But a mass-conservative correction added to the `pchip` regridding step (tested in a scratch copy only - real repo never touched) barely moved `dMBMn_max`/`dMBHfr_max`, ruling that step out as the dominant cause despite the jump-size correlation; phase-diagram data quality was checked and ruled out too (`KDMn` is proportionally *smoother* along the P-T path than MgO's own ratio, not noisier). The drift instead correlates strongly with interface velocity `v` (0.80 with `|v|` for Mn; -0.64 signed for Hfr, opposite-sign response to growth vs. resorption for the two species) - pointing at `solveBC`'s own boundary-value formula and its dependence on the externally-fixed, major-element-derived `v`. This is core solver numerics, and the authors want to confirm the approach before any change is made. See [Benchmarks](docs/benchmarks.md#results-full-resolution-full-duration-runs) for the full write-up.
- The GUI's Load Example feature and dark-mode toggle were built and confirmed to construct/run without error, but not yet visually inspected in an interactive session - please eyeball both once, and if the dark-mode contrast/colors need adjusting, the palette is three properties at the top of `MIDAS.m` (`DarkBg`/`DarkPanel`/`DarkText`).
