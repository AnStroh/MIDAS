# Cross-implementation consistency tests

`matlab/`, `GUI/`, and `octave/` are meant to be three independent copies of the *same* model (see the root [README](../README.md)). This folder checks that claim numerically: run the same six example configurations through each implementation and confirm they agree, field by field, within a tight tolerance - not just that each one runs without crashing (that's what each folder's own CI smoke test already checks).

## Usage

**1. Generate results** - from *within* each implementation you have access to (needs the matching interpreter: MATLAB for `matlab/`/`GUI/`, GNU Octave for `octave/`):

```
cd matlab
matlab -batch "addpath('../tests'); generate_results('matlab')"
```
```
cd GUI
matlab -batch "addpath('../tests'); generate_results('GUI')"
```
```
cd octave
octave --eval "addpath('../tests'); generate_results('octave')"
```

(Deliberately not `run('../tests/generate_results.m')` - both MATLAB's and Octave's `run()` change the working directory to the script's own folder for the call, which would break the example-file lookup.)

Each run saves one `.mat` file per example to `tests/results/`, named `<matlab|GUI|octave>_MIDAS_Params_ExampleN_*.mat`. You don't need all three - compare whichever you have.

**2. Compare** - once you have results from 2 or more implementations:

```
cd tests
octave --eval "compare_results"
```
or in MATLAB:
```matlab
compare_results   % default tolerance 1e-12
compare_results(1e-9)   % looser tolerance
```
(Run from `tests/`, or with `tests/` on the path.)

Reports, per example and per pair of implementations, any numeric field whose relative difference exceeds the tolerance. Timestamps, file paths, and mode-switch strings (`params.PTmode`, etc.) are skipped - those are validated by construction, since all three runs start from the identical `MIDAS_Params_ExampleN.m` input file.

## What this can and can't tell you

- Uses a reduced grid/duration (same as `.github/scripts/smoke_test.m`) for speed - this checks implementation *parity*, not physical accuracy at production resolution.
- **1e-12 is an intentionally tight default.** It's close to the scale where ordinary floating-point rounding, accumulated over a full many-timestep run, can differ between platforms even when both implementations are correct. `octave/` in particular uses a few mathematically-equivalent-but-not-necessarily-bit-identical substitutes for MATLAB-only functions (`interp1(...,'extrap')` for `griddedInterpolant`; `round(x*10^n)/10^n` for `round(x,n)` - see [`octave/README.md`](../octave/README.md#differences-from-the-matlab-version)). A field sitting just above 1e-12 is a prompt to look closer with a looser tolerance (e.g. `1e-9`), not automatically a real bug.
- This repo currently only has GNU Octave available to actually execute `octave/`'s generation step in an automated/agent context - `matlab/` and `GUI/` results need to be generated by someone with a MATLAB license.
